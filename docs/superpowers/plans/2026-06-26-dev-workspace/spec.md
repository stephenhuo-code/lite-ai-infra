# Spec — Dev Workspace(agent 数据开发台)

> WHAT / WHY。零实现细节(框架/端点/协议/沙箱实现归 [design.md](./design.md))。**面向非技术干系人可读。**
> 地基/外部依赖,**带 ADR**:[ADR-026](../../../adr/ADR-026-dev-workspace-omnigent.md)(omnigent 作 agent 后端 + 授权三分层)。外部依赖事实见 [spike RESULTS](../../spikes/2026-06-26-omnigent-feasibility.md)(omnigent 源码级实证)。
> **状态**:Draft · **关联出口**:S1 出口④ 降级项 **Plan 9**(从"code-server 半天版"升级为 agent 工作台,见 [ADR-019](../../../adr/ADR-019-exit5-gui-bff-resequence.md))· **输入**(owner 原话):"dev workspace = 左树右对话窗口结构;左树含工作目录、catalog、git 树;右边 agent 对话 + 文件显示;目标 = 基于数据目录的数据集做数据探查 + 数据管线开发(兼容 Data-Juicer 和 Python)。"

## Goal & 价值
- 给数据工程师一个 **agent 驱动的数据开发台**:在一个"左树(工作目录 / 数据目录 / git)+ 右侧(agent 对话 + 文件 + 终端)"的界面里,**对话式地**完成基于数据目录(catalog)数据集的**数据探查**与**数据管线开发**(Data-Juicer + Python)。
- 价值:把"探查→写管线→跑→把结果数据集注册回目录"这条数据准备链路,从手工写脚本/SSH 提速为对话式协作;agent 在受控沙箱内代劳脏活,人专注判断。成功 = 用户能在一个企业的真实数据集上,经 agent 完成一次端到端的数据准备并把产物落回数据目录。

## 范围
- **In(本 plan 做)**:
  1. **agent 工作台界面**:左树(工作目录 / 数据目录 catalog / git 树)+ 右侧(agent 对话 + 文件查看 + 终端),在现有控制台内作为新页。
  2. **数据探查**:用户经 agent 对选定数据集查看结构/采样/基本统计。
  3. **数据管线开发**:用户经 agent 编写并运行数据管线(**Data-Juicer recipe** 与 **Python 代码**),产物可**注册回数据目录**(归属=本人 owner)。
  4. **工作目录 + git**:agent 与用户在一个工作目录里产出脚本/文档;工作目录**跨会话持久化(按 workspace 为单位隔离保存)**,用 **本地 git** 做版本管理。
  5. **隔离与授权(承重)**:agent 只能经平台提供的能力访问数据,且访问受**企业硬隔离 + owner 授权**约束;agent 的代码执行限制在本人工作目录沙箱内;高风险行为可被拦截/需确认。
- **Out(本 plan 不做)**:多人实时协作同一会话的完整 UX;数据集的可视化图表预览;非数据场景的通用编程工作台。
- **推迟(v-next / backlog,带理由)**:
  - **多人协作会话**(谁能 view/edit/run 某会话)—— 底座能力具备([ADR-026](../../../adr/ADR-026-dev-workspace-omnigent.md) 会话协作层),但完整协作 UX 是独立增量,先稳单人主路径。
  - **细粒度/按 group 的数据授权** —— 沿用 v1 `can()`(企业 + owner);group/细粒度随 **Cerbos**([ADR-011](../../../adr/ADR-011-authorization-pdp-cerbos.md))引入,届时经"数据工具接缝"把 `can()` 换 Cerbos,不动 agent 后端(见 [ADR-026](../../../adr/ADR-026-dev-workspace-omnigent.md) §4)。
  - **Lance 列式 schema 深探 / 数据预览采样** —— 承接 catalog v-next(需后端读 Lance Arrow schema),本轮探查为"结构/采样/基本统计"级。
  - **云沙箱 / 多 harness** —— v1 本地沙箱 + 单一 agent harness;云沙箱(弹性算力)与多 harness 后续。
  - **远端 git 托管集成** —— v1 只做**本地 git**(工作目录内 init/commit/log/回溯);推送到外部托管(GitHub 等)**由用户自行配置**,平台不内建凭证/集成。
  - **per-企业模型路由 / 计费台账** —— 平台运营面,非本轮。
- **与现状对齐**:**授权沿用 owner 模型([ADR-024](../../../adr/ADR-024-owner-based-dataset-ownership.md))+ 现有 `can()`**;数据目录注册沿用 catalog-driven([ADR-023](../../../adr/ADR-023-catalog-driven-datasets.md));身份沿用 KC Organizations([ADR-025](../../../adr/ADR-025-keycloak-organizations-as-enterprise.md))。企业仍是硬隔离边界。

## User Scenarios & Testing *(必填)*

### US1 — agent 工作台与会话(左树右对话) (Priority: P1,地基)
用户进入「Dev Workspace」,看到左树(工作目录 / 数据目录 / git)与右侧 agent 对话区;发起一次会话,用自然语言让 agent 干活,并能看到 agent 的操作(改了哪些文件、终端输出)。

- **Why this priority**:这是整轮的骨架——没有"工作台 + 一个能跑的 agent 会话",探查/管线/git 都无处挂。
- **可独立测试**:打开工作台→发起会话→给 agent 一句指令(如"在工作目录建个 README 写上今天计划")→能看到文件出现、对话有回应。只此即一个可演示 MVP 切片。
- **验收场景**:
  1. **Given** 已登录的企业用户,**When** 打开 Dev Workspace,**Then** 看到左树(工作目录 / 数据目录 / git 三块)与右侧对话区。
  2. **Given** 一个会话,**When** 用户发自然语言指令,**Then** agent 执行并在对话区回应,左树/文件区**可观察到**其产出(文件变化、终端输出)。
  3. **Given** agent 在工作,**When** 用户查看,**Then** agent 的关键动作(运行命令、读写文件)对用户**可见**(非黑盒)。

### US2 — 基于数据目录数据集的数据探查 (Priority: P1,核心价值)
用户从左树的数据目录选中一个数据集,让 agent 探查它:看结构、采样几条、给出基本统计概览。

- **Why this priority**:这是工作台的第一份真实业务价值,且独立可演示。
- **可独立测试**:选一个真实数据集→让 agent "看看这个数据集长什么样"→对话区/文件区给出结构 + 样本 + 基本统计。
- **验收场景**:
  1. **Given** 数据目录里有本企业的数据集,**When** 用户让 agent 探查某数据集,**Then** agent 返回其结构/格式、若干样本与基本统计概览。
  2. **Given** 探查动作,**When** agent 访问该数据集底层数据,**Then** 访问**经平台能力 + 授权**完成(用户无需手填密钥/路径)。
  3. **Given** 用户对**本企业内无权访问**(非本人私有且未共享)的数据集发起探查,**When** agent 尝试,**Then** **被拒**且对用户有可理解反馈。

### US3 — 隔离与授权不被破坏 (Priority: P1,承重)
工作台引入了一个能写代码、跑命令、读数据的 agent;它绝不能成为绕过企业硬隔离 / owner 授权 / 主机安全的后门。

- **Why this priority**:agent 是高能力主体;隔离若被打穿则整轮失败,且违反架构宪法红线。
- **可独立测试**:构造越权/越界尝试(跨企业读数据、逃出工作目录、危险命令),逐一被拦。
- **验收场景**:
  1. **Given** 属于企业 A 的用户,**When** 其 agent 试图访问企业 B 的数据,**Then** **被拒**(企业硬隔离不被绕过)。
  2. **Given** agent 在工作目录运行代码,**When** 它试图读写本人工作目录/会话之外的主机文件或他人工作目录,**Then** **被阻止**(沙箱不逃逸)。
  3. **Given** agent 要访问数据,**When** 发生访问,**Then** **只能经平台提供的数据能力**且**每次访问受企业 + owner 授权约束**;**MUST NOT** 存在绕过授权的旁路。
  4. **Given** agent 触发高风险行为(如危险 shell 命令),**When** 发生,**Then** 该行为**被拦截或需人确认**后才执行。
  5. **Given** 一个**未归属任何企业**的账户进入工作台,**When** 其试图开展数据工作,**Then** 系统**明确处理**(拒绝/引导),**MUST NOT** 悬空或绕过隔离。

### US4 — 数据管线开发(Data-Juicer + Python),产物注册回目录 (Priority: P2)
用户经 agent 编写并运行数据管线:既可写 Data-Juicer recipe,也可写 Python 代码;跑出的处理后数据集能注册回数据目录,归属为本人。

- **Why this priority**:核心目标之一,但建立在 US1/US2 之上;探查可先独立交付。
- **可独立测试**:让 agent 基于某数据集写一个简单 DJ recipe(或 Python)→运行→产出处理后数据集→注册回数据目录,能在目录里看到这条新数据集(owner=本人)。
- **验收场景**:
  1. **Given** 一个数据集,**When** 用户让 agent 写并运行一个 Data-Juicer 管线,**Then** 管线在受控环境内执行并产出处理后数据。
  2. **Given** 同样场景,**When** 用户要求改用 Python 代码处理,**Then** 也能编写并运行(两种方式都支持)。
  3. **Given** 管线产出,**When** 用户把它注册回数据目录,**Then** 数据目录出现该处理后数据集,**归属为本人(owner)**,落在本企业边界内。

### US5 — 工作目录持久化 + 本地 git 版本管理 (Priority: P2)
工作目录**跨会话持久化**(按 workspace 为单位隔离保存);里面的脚本/recipe/文档用**本地 git** 管理;左树能看到 git 状态,用户可经 agent 或界面提交版本。会话中断/重开后,工作目录与已提交版本仍在。

- **Why this priority**:让"开发"可迭代、可回溯、不丢工作;非首份价值,故 P2。
- **可独立测试**:在工作目录改一个文件→git 状态反映改动→提交→关闭会话再重开,文件与该提交仍在。
- **验收场景**:
  1. **Given** 工作目录有改动,**When** 用户查看左树 git,**Then** 看到当前改动/状态。
  2. **Given** 用户要保存一版,**When** 经界面或 agent 提交,**Then** 改动进入**本地**版本历史、可回溯。
  3. **Given** 会话中断或用户重新进入工作台,**When** 重开同一 workspace,**Then** 工作目录内容与已提交版本**仍在**(持久化)。
  4. **Given** 用户想推送到外部 git 托管,**When** 本轮范围内,**Then** 这属**用户自行配置**(平台不内建),不在 v1 验收内。

### Edge Cases(边界 / 异常)
- 当 agent 试图访问**跨企业**或**本人无权**的数据时会怎样?(US3-1/US2-3)
- 当 agent 的代码试图**逃出工作目录沙箱**或访问主机/他人文件时会怎样?(US3-2)
- 当 agent 要执行**危险命令**(删文件、外联、提权)时会怎样?(US3-4)
- 当**未归属企业**的用户进入工作台时会怎样?(US3-5)
- 当管线/代码**长时间运行、消耗过大算力或模型成本**时如何处理?
- 当 **agent 后端不可用 / 会话中断**时,用户工作目录与已提交版本仍在(工作目录持久化保存),重开 workspace 可恢复。
- 当**模型凭证缺失/失效**时,工作台如何反馈而非泄露密钥?
- 当一个用户**同时开多个会话**或多次重复注册同名产出数据集时会怎样?

## Requirements *(必填)*

### 功能需求(可测)
- **FR-001**:用户 MUST 能在一个统一界面里看到**左树(工作目录 / 数据目录 / git)**与**右侧(agent 对话 + 文件查看 + 终端)**。
- **FR-002**:用户 MUST 能与 agent **对话式协作**,并能**观察** agent 的关键动作(文件变化、命令与输出)。
- **FR-003**:用户 MUST 能让 agent **探查数据目录中的数据集**(结构/格式、样本、基本统计)。
- **FR-004**:用户 MUST 能让 agent **编写并运行数据管线**,**兼容 Data-Juicer recipe 与 Python 代码**两种方式。
- **FR-005**:用户 MUST 能把管线**产出的数据集注册回数据目录**,归属为本人(owner),落在本企业边界内。
- **FR-006**:工作目录 MUST **跨会话持久化**(按 workspace 为单位隔离保存),会话中断/重开后内容与版本历史仍在。
- **FR-006b**:工作目录 MUST 支持**本地 git 版本管理**(查看状态、提交、回溯);推送外部 git 托管为用户自行配置(本轮不内建)。
- **FR-007**:agent 对数据的访问 MUST **只经平台提供的数据能力**进行,且**每次访问受企业硬隔离 + owner 授权约束**;系统 MUST NOT 提供绕过授权的数据旁路。
- **FR-008**:系统 MUST NOT 允许 agent 访问**调用者企业 / owner 边界之外**的数据。
- **FR-009**:agent 的代码执行 MUST 被限制在**本人工作目录 / 会话沙箱**内,MUST NOT 逃逸到主机或他人工作目录。
- **FR-010**:**高风险 agent 行为**(如危险 shell 命令)MUST 可被**拦截或要求人确认**后才执行。
- **FR-011**:**未归属任何企业**的账户进入工作台 MUST 被**明确处理**(拒绝 / 引导),MUST NOT 悬空或借此绕过隔离。
- **FR-012**:模型 / 后端凭证 MUST NOT 出现在代码库或前端,MUST 以受管密钥形式注入。
- **FR-013**:系统 SHOULD 能对单会话的**算力 / 模型成本**施加上限或可观测约束,避免失控消耗。

### 关键实体(概念级,涉及数据时填)
- **工作台会话(Workspace Session)**:一次 agent 协作的上下文(归属某用户、某企业);承载对话、工作目录与运行环境。
- **Workspace / 工作目录(Working Directory)**:agent 与用户协作产出脚本/recipe/文档的目录,**以 workspace 为单位跨会话持久化、按 owner 隔离**;agent **默认有权读写本 workspace 目录**(此即其沙箱边界),受本地 git 管理。注意区分:对**本目录**默认可访问,对**数据集(catalog/OSS)**则须经平台数据能力 + 授权(见下条)。
- **数据集(Dataset)**:数据目录中的一等条目(沿用 catalog-driven),探查与管线的输入/输出;归属 owner、属某企业。
- **数据管线(Pipeline)**:对数据集的处理逻辑,表达为 Data-Juicer recipe 或 Python 代码;运行产出新数据集。
- **平台数据能力(Data Capability)**:agent 访问数据/运行管线的**唯一受控通道**;每次调用经企业 + owner 授权(概念,非实现)。

## Success Criteria *(必填)*
- **SC-001**:用户能从打开工作台到经 agent 完成**一次数据集探查并看到结果**,在 **5 步对话内 / 数分钟内**完成。
- **SC-002**:隔离负例(跨企业读数据、逃出沙箱、绕过授权旁路、危险命令未确认即执行)**100% 被拦**,无一通过。
- **SC-003**:至少在 **1 个真实企业数据集**上跑通端到端:**探查 → 写管线(DJ 与 Python 各一次)→ 运行 → 注册回数据目录**,产物在目录中可见且归属正确。
- **SC-004**:agent 代码执行**零例**逃逸出本人工作目录沙箱(图形化验收 + 负例测试观测)。
- **SC-005**(定性):数据工程师认为"左树右对话"的工作台比原 code-server 方案**更易完成数据准备任务**。

## Assumptions(假设与依赖)
- 依赖 **omnigent**(self-host)作 agent 后端(运行时 + 沙箱 + 行为策略),依赖**现有 KC 认证**、**catalog-driven 注册**、**owner 模型 + `can()`**、**现有 Data-Juicer 管线**。
- v1 面向**单人**主路径:一个用户在自己的工作目录/会话内工作;多人协作同一会话推迟 v-next。
- v1 数据探查为"结构/格式 + 样本 + 基本统计"级;Lance 列式深探/可视化预览推迟。
- v1 用本地沙箱 + 单一 agent harness;云沙箱/多 harness 推迟。
- **工作目录持久化(owner 2026-06-26 拍定)**:以 **workspace 为单位持久化到对象存储**,按 workspace 隔离;agent **默认授权访问本 workspace 目录**。git **仅本地实现**(工作目录内 init/commit/log);远端 git 由用户自行配置。
- 以下形态**留 design + Task0 探针实测钉死**(已记于 design,非静默猜):平台数据能力的确切集合与与现有 DJ 管线的复用边界、前端↔agent 后端的鉴权形态、模型接入与成本治理策略、agent 后端版本钉定、(承上)对象存储工作目录与 agent 沙箱本地盘的挂载/同步形态。
