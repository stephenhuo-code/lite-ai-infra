# Spec — 用 Keycloak Organizations 作为「企业」+ 注册/邀请自动归属

> WHAT / WHY。零实现细节(claim 形态/端点/realm 配置归 design)。地基级身份变更,**带 ADR**(supersede/amend [ADR-010](../../../adr/) 两级租户、amend [ADR-016](../../../adr/ADR-016-gravitino-tenancy-mapping.md));调研事实见 [spike](../../spikes/2026-06-23-kc-organizations-vs-groups.md)(KC 26.6.2 实测)。

## 出口与范围
- **关哪个**:把「企业(enterprise)」从**文化约定的路径前缀**(KC realm group `/e-XXXX`)升级为**结构化的一级身份实体**(Keycloak Organization)。企业相关能力(归属、注册自动落企业、邀请)对应到 org 这一级。**附带解决**之前"自助注册→无企业→撞 403"(huo 那类)的缺口。
- **In**:
  1. 企业 = KC Organization(**不透明标识**,不再人工编码 `e-XXXX`)。
  2. 用户的企业归属从 **org 成员关系**推导,身份上下文据此驱动现有隔离/授权,**不破坏**既有企业硬隔离与数据读写。
  3. **自助注册 + 邮箱域自动归企业**:新用户按其邮箱域自动成为对应企业成员。
  4. **邀请加入企业**:企业管理员邀请用户加入(含非该域邮箱)。
  5. **身份降为两级租户(平台 → 企业 → 用户),移除"访问组"层**:"group"(现 `g-XXXX`)从身份层级移除;企业内角色仅 **member / enterprise-admin**。
  6. 企业标识不透明化后,所有按企业隔离/命名的下游(对象存储路径、元数据租户、契约校验、审计)**一致切到新标识**。
  7. 既有用户切换到 org 模型(v1 清晰切换)。
- **Out / 推迟(v-next,带理由)**:
  - **资源授权的 "group" 维度 = Cerbos** —— v1 授权只按 **企业(硬隔离)+ owner**;"对资源(OSS/数据集)按 group 授权"随 **Cerbos** 引入,届时 group 是**授权主体集合**(可由 KC group / Organization Groups / Cerbos 自管,实现时定),**与身份层级解耦**。本轮**不建任何访问组结构**。原 `group-admin` 的细粒度授权能力一并随 Cerbos 回归。
  - **自助注册按邮箱域自动归属** —— 与"用户名+密码同页登录"冲突(KC 按域自动归属只绑 identity-first,见 design/ADR-025);v1 加入企业由**企业管理员授予**;域自动归属需后端自建(邮箱域→入会+刷新 token),v-next。
  - **邀请完整接受流** —— 端点已实现,完整 e2e 依赖 prod 真 SMTP(dev 用 mailpit 可验);上线时配真邮件服务。
  - **per-org 企业级 SSO(每企业绑自己 IdP)** —— org 的 B2B 大价值,但独立增量,本轮不做(身份地基先稳)。
  - **多企业用户(一个用户属多个企业)** —— v1 单企业/用户够用;多企业(unmanaged 成员)后续。
  - **企业自助开通/计费/配额台账** —— 平台运营面,非本轮。
  - **企业邮箱域的后期改/删对已归属成员的影响** —— v1 仅"建 org 时登记域 + 拒重复登记同域";域的增改删与对存量成员的重算,v-next。
- **与现状对齐**:**授权沿用 owner 模型([ADR-024](../../../adr/ADR-024-owner-based-dataset-ownership.md))+ 现有 `can()`**;数据集归属(owner=上传用户)**不动**——本轮只换"企业这一层的来源与标识",企业仍是硬隔离边界;**v1 移除访问组层,"按 group 授权" 留 Cerbos**。

## 用户故事(按优先级,可独立测试)

### US1 — 企业是结构化的一级实体(P1,地基)
**Why P1**:这是整轮的地基——没有 org 作企业,后面"自动归属/邀请/per-org"都无处挂。
**可独立测试**:运维建一个企业(org)→ 它作为一级实体存在、有稳定标识;把一个用户加入它 → 该用户的身份里带有"属于这个企业"。
- **AC1**:Given 平台运维,When 新建一个企业,Then 该企业作为**结构化实体**存在(可增删改查、可加成员),拥有**稳定的不透明标识**。
- **AC2**:Given 一个用户被加入某企业,When 他登录,Then 系统能从其身份**可靠地解析出他属于该企业**(不依赖资源名/路径前缀的约定)。
- **AC3**:Given 资源/界面展示,When 涉及企业标识,Then **MUST NOT 暴露语义编码**(§1.4 不透明 ID),界面用企业显示名、不渲染内部标识。

### US2 — 企业隔离与现有授权不被破坏(P1,承重)
**Why P1**:企业是硬隔离边界;换来源/换标识若打穿隔离或回归现有数据流,则整轮失败。
**可独立测试**:同企业用户能访问本企业数据;跨企业访问被拒;平台管理员仍只走特权口;既有上传→注册→管线全链路在新企业标识下仍跑通。
- **AC1**:Given 用户属于企业 A,When 他访问企业 B 的资源,Then **被拒**(企业硬隔离不被绕过)。
- **AC2**:Given 平台管理员,When 他走普通业务 API,Then **被拒**(仍只能走 `/admin/*`)。
- **AC3**:Given 既有数据流(上传/注册/管线/数据目录),When 企业来源改为 org、标识改不透明,Then 全链路**仍正确**(企业隔离 + owner 归属语义连续),既有质量门禁全绿。
- **AC4**:Given 平台管理员账户**不属于任何企业**(无 org 成员关系),When 他登录,Then 系统**按特权账户处理直达 `/admin/*`**,**MUST NOT** 把他卷进 US3 的"无企业/待分配"注册流程或误导提示。

### US3 — 注册 + 企业管理员授予加入(P1;域自动归属 v-next)
> **修订(2026-06-26,owner 选 C)**:原"自助注册按邮箱域**自动**归企业"显式推迟 v-next —— 实测 KC 26.6.2 的按域自动归属只绑 identity-first 登录,与"用户名+密码同页登录"冲突(见 design/ADR-025)。v1:**注册建账号 + 企业管理员授予成员关系**(加入企业由管理员处理,合理);未归属账号进"待分配"显式态。
**Why P1**:修掉"注册→无企业→撞 403"缺口的方式改为**管理员授予 + 显式待分配态**(不静默悬空)。只做 US1+US2+US3 即可演示 MVP(建企业→管理员加成员→能用)。
**可独立测试**:用已登记邮箱域的邮箱自助注册 → 登录后已是对应企业成员、能见到/上传本企业数据,不撞无企业错误。
- **AC1**:Given 某企业登记了邮箱域 `@acme.com`,When 用 `x@acme.com` 自助注册,Then 注册完成后该用户**自动成为该企业成员**。
- **AC2**:Given 上述用户首次登录,When 进入控制台,Then 他**直接能用**(上传/见到本企业数据),**不会**因"无企业"被拒。
- **AC3**:Given 用一个**未登记任何企业域**的邮箱注册,When 注册,Then 系统**明确处理**(显式拒绝或置为"待邀请/待分配",并给可理解提示)——**MUST NOT** 静默产生一个无企业、一进业务就撞 403 的悬空账户。

### US4 — 邀请加入企业(P2)
**Why P2**:覆盖"非企业邮箱域成员/受控加入"场景;晚于"域自动归属"主路径。
**可独立测试**:企业管理员发邀请 → 受邀者凭邀请加入 → 成为该企业成员。
- **AC1**:Given 企业管理员,When 他对某邮箱发起加入邀请,Then 受邀者收到可接受的邀请。
- **AC2**:Given 受邀者接受邀请,When 完成,Then 他**成为该企业成员**(身份里带该企业),即便其邮箱域不属于该企业。
- **AC3**:Given 一个已过期/已撤销的邀请,When 被使用,Then **被拒**并给出原因。

### US5 — 身份降为两级租户,移除"访问组"层(P1)
**Why P1**:owner 模型(ADR-024)后访问组在 v1 不参与任何授权决策,却硬塞在身份层级里(`/e-XXXX/g-YYYY/`)是空壳结构。本轮把身份层级简化为 **平台 → 企业(org)→ 用户**;"group"从身份层级移除,改为**未来 Cerbos 的资源授权维度**(与身份层级解耦)。这降低本 plan 风险(不碰 realm 子组双树、不沾 org-groups 新特性)。
**可独立测试**:用户身份只解析出"属于哪个企业 + 企业内角色(member/enterprise-admin)",无访问组层;授权(企业硬隔离 + owner)与改造前一致、不回归。
- **AC1**:Given 企业=org、无访问组层,When 用户登录,Then 身份上下文解析出 **(企业, 角色∈{member, enterprise-admin})**,**不含**访问组维度。
- **AC2**:Given 数据访问,When 用户访问资源,Then 授权只由 **企业(硬隔离)+ owner(归属)** 决定(与 owner 模型一致),"按 group 授权资源"**留待 Cerbos**。
- **AC3**:Given 现有角色 `group-admin`(依附访问组),When 移除访问组层,Then `group-admin` **不再存在**;企业内仅 `member` / `enterprise-admin` 两级(原 group-admin 的细粒度授权能力随 Cerbos 回归)。

### US6 — 既有用户/数据切换到 org 模型(P1,迁移)
**Why P1**:不切换则新旧并存、隔离判定二义;必须有清晰切换路径。
**可独立测试**:对现有企业/用户执行一次切换 → 用户仍能访问其原企业数据;跨企业仍隔离;切换可重复执行(幂等)。
- **AC1**:Given 现有用户(原属 `/e-XXXX` group),When 执行切换,Then 他成为对应 org 的成员,登录后企业归属正确。
- **AC2**:Given 现有企业的数据(dev 可重建;prod v1 无数据),When 企业标识改不透明,Then 数据在**新标识下可被同企业用户正确访问**(v1 为清晰切换,非在线数据迁移)。
- **AC3**:Given 切换脚本重复执行,When 再跑一次,Then **幂等**(不重复建 org/成员、不破坏既有)。

### Edge Cases
- 用**无匹配企业域**的邮箱注册 → 怎样?(见 US3-AC3:显式处理,不悬空)
- 一个用户被加入**多个企业** → v1 怎样?(v1 单企业;多企业显式推迟,身份解析需明确取哪个/拒绝二义)
- 企业**邮箱域冲突**(两个企业登记同一域)→ 注册归哪个?(需明确规则:拒绝重复登记 / 优先级)
- 企业的**身份 claim 未带到令牌**或多企业 claim "消失"(spike 已知坑)→ 身份解析必须明确失败、不静默放行。
- 切换中途失败/部分完成 → 必须可重试且不留半态(幂等)。
- 平台管理员账户(无企业归属)→ 仍按特权账户处理,不被"无企业"逻辑误伤。

## 功能需求(MUST,可测)
- **FR-001** 企业 MUST 是**结构化一级身份实体**(非路径约定),有**稳定不透明标识**;界面/资源名 MUST NOT 暴露语义编码企业 ID(§1.4)。
- **FR-002** 用户的企业归属 MUST 从其**身份(org 成员关系)**可靠推导;身份上下文 MUST 产出"用户所属企业 + 企业内角色(member/enterprise-admin)"以驱动**现有 `can()` 与企业硬隔离**,且 MUST NOT 破坏既有数据读写。**MUST NOT** 含访问组维度。
- **FR-002b** 企业 MUST 有**显示名(display_name)**;面向用户的接口 MUST 返回企业显示名供界面渲染(企业标识不透明后,界面 MUST 显示名而非不透明 ID,§1.4)。
- **FR-003** 自助注册 MUST 创建账号;**加入企业 MUST 由企业管理员授予**(或邀请)。注册后未归属企业的账号 MUST 进入**显式"待分配"态**(进业务时显式拒 + 可理解提示),MUST NOT 静默悬空到处撞 403。**按邮箱域自动归属 = v-next**(需后端自建,见 design)。
- **FR-004** 企业管理员 MUST 能**邀请**用户加入本企业;受邀者接受后 MUST 成为该企业成员;过期/撤销邀请 MUST 被拒。
- **FR-005** 身份层级 MUST 为两级租户(平台 → 企业 → 用户),**MUST NOT 含"访问组"层**;企业内角色 MUST 仅 **member / enterprise-admin**;"按 group 授权资源" MUST 留待 Cerbos(与身份层级解耦)。
- **FR-006** 企业标识不透明化后,所有按企业隔离/命名的下游(对象存储路径前缀、元数据租户、契约校验、审计字段)MUST 一致使用新标识,MUST NOT 残留旧 `e-XXXX` 编码假设。
- **FR-007** 跨企业 MUST 隔离;平台管理员 MUST 仍只能走 `/admin/*` 特权路径。
- **FR-008** 本轮 MUST NOT 破坏既有 CI 与既有数据集读写;授权沿用 owner 模型 + 现有 `can()`,**数据集归属(owner)不变**。

## 关键实体(概念)
- **企业(Enterprise)**:一级身份实体(KC Organization)。属性:**不透明标识**、显示名、登记的邮箱域、成员、(可空)绑定身份源。是**硬隔离边界**。
- **企业成员关系(Membership)**:用户 ↔ 企业的从属关系,携带该用户在企业内的**角色**(无访问组维度)。
- **角色(Role)**:**member / enterprise-admin**(企业内两级权限);`group-admin` 随访问组层移除,其细粒度授权随 Cerbos 回归。
- **(v-next)资源授权 group 维度**:未来 Cerbos 中"对资源(OSS/数据集)按一组用户授权"的主体集合;**与身份层级解耦**,v1 不建。
- **邀请(Invitation)**:把用户受控纳入某企业的凭据(可过期/撤销)。
- **邮箱域归属规则(Domain Mapping)**:邮箱域 → 企业的映射,驱动注册自动归属。

## Success Criteria(可度量、技术无关)
- **SC-001**:新建一个企业 + 加入一个用户 → 该用户登录后身份**正确解析出该企业 + 角色**;跨企业访问被拒。
- **SC-002**:自助注册建账号;**企业管理员授予加入**后,该用户登录即可上传/见到本企业数据;未授予前为显式"待分配"态(不静默撞 403)。
- **SC-003**:邀请流程:管理员发邀请 → 受邀者接受 → **成为成员**;过期邀请被拒。
- **SC-004**:既有用户切换后仍能访问其**原企业数据**(语义连续),跨企业仍隔离;切换脚本**幂等**。
- **SC-005**:既有质量门禁(生成/静态/测试)**全绿**;既有上传→注册→管线→数据目录全链路在新企业标识下**不回归**。
- **SC-006**:界面/资源名**不暴露**语义编码企业 ID(§1.4);界面**显示企业 display_name 而非不透明 ID**。
- **SC-007**:端到端冒烟:建企业→(域自动归属 或 邀请)注册/加入→登录→上传→注册数据集→跑管线 **全程在新企业标识下跑通**。

## Assumptions
- KC **26.6.2**(实测,spike);Organizations 核心 GA(26.0)。**v1 身份两级(企业+用户),不设访问组层**;**资源授权 group 维度(Cerbos)/ per-org SSO / 多企业用户 显式 v-next**。
- **v1 prod 无数据**(未 GA)→ 企业标识改不透明是**清晰切换**,非在线数据迁移;**dev 数据可重建**。
- 角色仅 **member / enterprise-admin**,用 org 属性 / realm role 表达(design 定),**不依赖访问组路径**;`group-admin` 移除。
- 授权沿用 **owner 模型(ADR-024)+ 现有 `can()`**;企业仍硬隔离;**"按 group 授权资源" = Cerbos(与身份层级解耦,v1 不建访问组)**。数据集归属(owner=上传用户)**本轮不动**。
- **token 的企业 claim 实际形态、多-org 行为、是否进 access token、邮箱域自动归属与邀请的真实流程 = 探查优先**(probe-first,起真 KC 26.6.2 实测钉死;spike 记了预期形态 + 5 个已知坑作探针清单)。
- 持久化与本地环境单一源沿用已合并的 env-config;前端控制台沿用已合并的数据域控制台(账户页"企业/组显示名"缺口本轮可一并补真实企业显示名)。
